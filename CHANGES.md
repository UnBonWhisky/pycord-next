# Changes from pycord to pycord-next

This file tracks every difference between `py-cord` (master @ `a4fee6d5`) and pycord-next.

Each entry is classified as:

- **Breaking** — existing code must be changed (the `pycord-migrate` tool rewrites most of them).
- **Major** — new feature or significant behaviour addition, existing code keeps working.
- **Minor** — small additions, fixes, internal changes with no impact on user code.

Entries reference the upstream PR or Discord documentation they come from when relevant.

## Breaking

### Caching

The cache can live in Redis, so a cache read may do I/O. Why: making the lookups awaitable now avoids a second break the day a bot switches backend. Only what has no synchronous equivalent in a remote cache is awaited:

- the `get_*` lookups by id (`await client.get_guild(id)`, `await guild.get_member(id)`...), because they are the calls that read the cache one entity at a time;
- the generators and the coroutines that must walk or empty the cache (`get_all_channels()`, `get_all_members()`, `clear()`).

Everything else that reads the cache keeps its pycord name, its behaviour and its synchronous form on the default in-process cache: `client.guilds`, `guild.members`, `member.roles`, `channel.permissions_for()`, `message.channel`, ... With a remote backend those raise `SyncCacheAccessError` (relationship attributes return a partial handle instead) and their awaitable twin is used, see Major / Caching.

**Client**

| Old | New |
|---|---|
| `client.get_channel(id)`, `get_message`, `get_stage_instance`, `get_guild`, `get_user`, `get_emoji`, `get_sticker`, `get_poll`, `get_sound` | `await client.get_channel(id)` and the same names, awaited |
| `for c in client.get_all_channels()`, `for m in client.get_all_members()` | `async for c in client.get_all_channels()`, `async for m in client.get_all_members()` |
| `client.clear()` | `await client.clear()` (the cache backend may need I/O to be emptied) |

**Guild**

| Old | New |
|---|---|
| `guild.get_channel(id)`, `get_thread`, `get_channel_or_thread`, `get_member`, `get_member_named`, `get_role`, `get_emoji`, `get_stage_instance`, `get_scheduled_event`, `get_sound` | the same names, awaited; `await guild.get_sticker(id)` is new |

Every other property and method of `Guild` (`channels`, `members`, `roles`, `me`, `owner`, `chunked`, `by_category()`, ...) is unchanged.

**Internals that subclasses and extensions can hit**

- `ConnectionState`: every store and lookup helper (`store_user`, `store_emoji`, `store_sticker`, `maybe_store_app_emoji`, `store_poll`, `_get_guild`, `_add_guild`, `_remove_guild`, `_get_message`, `_get_private_channel`, `_add_private_channel`, `add_dm_channel`, `get_channel`, `get_user`, `get_emoji`, `get_sticker`, `get_poll`, `_get_sound`, `deref_user`, `chunk_guild`...) is a coroutine, and so are `is_guild_evicted()` and `process_chunk_requests()`. The properties `guilds`, `emojis`, `stickers`, `polls`, `private_channels` and `sounds` still exist and read the in-process cache, next to the awaitable `get_guilds()`, `get_emojis()`, ... `ConnectionState.parsers` maps every event to a coroutine function and `Client._handle_event` awaits it, so a state subclass overriding `parse_x` must define `async def parse_x`. Why: the parsers read and write the cache.
- Models are built synchronously and never read the cache in their constructors; what used to be resolved there (cached members, roles, threads, polls, emojis...) is done by the state afterwards (`await state._populate_guild(guild, data)`, `await state._create_message(...)`) or lazily by a property when it is read. `Guild`, `Thread` and `Message` no longer hold dictionaries of other entities, so `Guild._sync` and `Message._rebind_cached_references` are removed (a re-created guild needs no rebinding).
- `Guild._add_channel`, `_add_member`, `_remove_member`, `_add_role`, `_remove_role`, `_add_thread`, `_update_voice_state`, `_get_and_update_member`... and `Thread._add_member`/`_pop_member` are coroutines. Why: they write to the cache.

### Gateway

- `Client.ws` is a read-only property: the shard-0 `DiscordWebSocket` while connected with the default transport, `None` otherwise (custom transport, not connected, `AutoShardedClient` before its shards launched). Why: avoids a future break, the client can run on a transport without any websocket. `DiscordWebSocket` no longer has the command helpers `change_presence`, `request_chunks`, `voice_state` and `request_soundboard_sounds`; they are methods of `GatewayTransport` (`client._get_websocket(guild_id)` returns the transport). Why: avoids a future break, commands must work for any transport (broker, proxy), not only for a direct websocket.
- `AutoShardedClient.launch_shard()`, `launch_shards()` and the internal `Shard`, `EventType` and `EventItem` of `discord.shard` are removed; the shards are owned by `discord.gateway.ShardManager`. Why: avoids a future break, shard lifecycle and bucketed launch live in one manager that transports plug into.
- The default `Client.before_identify_hook` no longer sleeps 5 seconds: the identify concurrency of Discord is handled by the library (see Major / Gateway). Overrides keep being called with the same arguments; `initial` is `True` for the first shard of `shard_ids` only, as before. Why: the default sleep made every parallel bucket wait, spacing is now the `IdentifyLimiter`'s job.

### Commands

- The `command` of a `"delete"` action returned by `Bot.get_desynced_commands()` is the payload Discord returned (a `dict` with `id`, `name`, ...) instead of the command name. Only code that overrides the sync or reads that list is affected. Why: avoids a future break, the sync keeps every field of a registered command, which `delete_existing=False` needs to send it back untouched ([pycord #3325](https://github.com/Pycord-Development/pycord/pull/3325)).

- The helpers `GuildChannelConverter._resolve_channel()` / `_resolve_thread()` and `PartialMessageConverter._resolve_channel()` are coroutines, and the predicates created by `has_role`, `has_any_role`, `bot_has_role`, `bot_has_any_role`, `has_permissions`, `bot_has_permissions`, `has_guild_permissions`, `bot_has_guild_permissions` and `is_nsfw` are coroutine functions (`check.predicate` was already awaitable). Only code that subclasses the converters or calls an entry of `Command.checks` directly is affected. Why: avoids a future break, the converters and the checks resolve guilds, members, roles and channels through the awaited cache lookups so they work with every cache backend.

### Voice

- `discord.voice.utils.buffer.Buffer` and `BaseBuff` are removed, `JitterBuffer` stands alone (`len()`, `is_ready()`), and `PacketDecoder` no longer makes `FakePacket`s for lost packets (the jitter buffer just skips them). They are internals of the receive pipeline, not documented. Why: avoids a future break, the receive pipeline is no longer built on a generic buffer protocol.
- `VoiceConnectionState.self_voice_state` (property reading `guild.me.voice`) is replaced by `await VoiceConnectionState.get_self_voice_state()`, and `_update_voice_channel()` is a coroutine. They are internals of the voice connection, not documented. Why: avoids a future break, the connection reads the cache through awaited lookups so it works with any cache backend.

### Models

| Old | New |
|---|---|
| `Attachment.to_dict()["spoiler"]` | `Attachment.to_dict()["is_spoiler"]` (the documented attachment request field, see "Attachment Request Structure" of the message resource); `"flags"` is included when set. Why: `spoiler` is not a Discord field, so the flag was silently ignored when attachments were sent back by `Message.edit(attachments=...)` |
| `Attachment.to_dict()` leaves `"description"` out when it is empty | an empty description is sent as `""`, only `None` is left out, so that `Attachment.with_changes(description="")` can clear it |

## Major

### Caching

**Backend-agnostic cache** (`discord/cache/`, built on [aiocache](https://aiocache.aio-libs.org)). A `CacheStore` wraps any aiocache backend and hands out typed `CacheBucket[K, V]` collections (`get`, `get_many`, `set`, `set_many`, `pop`, `contains`, `keys`, `values`, `items`, `count`, `clear`, all awaitable, plus the synchronous `*_nowait` reads below) namespaced as `{namespace}:{kind}[:{scope}]`.

- Default is an in-process `SimpleMemoryCache` that stores live objects, so the default behaviour and speed stay the same (about 2 µs per awaited lookup). Redis (`pip install py-cord[redis]`) and other aiocache backends store slotted models through a generic msgpack `ModelSerializer`; bucket key listing and eviction order are kept in a `RedisIndex` (sorted set), so several processes can share one cache.
- **No TTL**: nothing ever expires. Limits are count based and identical to the old caches: `max_messages` (oldest message evicted first, `None` disables the cache) and the private channel LRU of 128 (a hit moves the channel to the end, the oldest is evicted first).
- **Client options** `cache_backend`, `cache_namespace` and `cache_fetch`, accepted by `Client`, `Bot`, `AutoShardedClient` and `AutoShardedBot`. They are wired into `ConnectionState`: every entity cache (users, guilds, emojis, stickers, polls, sounds, private channels, messages, and per guild the channels, threads, members, roles, voice states, scheduled events, stage instances, sounds, emojis and stickers) is a bucket of the store, `get_channel()` finds a channel through a `channel_guild` index instead of iterating every guild, and a `GUILD_DELETE` drops the guild's buckets together with its emojis, stickers, sounds and messages. A wrong `cache_backend` raises `TypeError`, a wrong `cache_namespace` `ValueError`.
- **`cache_fetch=True`** stores the result of every `fetch_*` that returns a cacheable entity (users, guilds, channels, threads, messages, members, roles, emojis, stickers, scheduled events, stage instances, sounds) through one helper, `ConnectionState._cache_fetched()`, with the same limits as gateway events: `max_messages` for messages, `MemberCacheFlags` for members (members are not stored when no flag is enabled).
- `ModelSerializer` also stores `array.array` subclasses (`SnowflakeList`) and classes, and a model can leave a back-reference out with `__cache_skip__` and rebuild it with `__cache_restore__`. The embed value objects, `Poll` and its parts, `PrimaryGuild`, `Collectibles`, `RoleColours`, `Object`, `MessageCall`, `MessageSnapshot`, `PartialMessageable` and a few others got `__slots__` so every cached model round-trips (tested for both the memory and the Redis backend).

```python
from aiocache import RedisCache

bot = discord.Bot(cache_backend=RedisCache(endpoint="localhost"), cache_namespace="mybot", cache_fetch=True)
```

**Synchronous accessors for the in-process cache, awaitable twins for every backend**. Every pycord property and synchronous method that reads the cache keeps its name, its behaviour and its synchronous form on the default cache. Cache buckets have `*_nowait` reads (`get_nowait`, `values_nowait`, `items_nowait`, `keys_nowait`, `count_nowait`, `contains_nowait`) and `CacheStore.supports_sync`; with a remote backend they raise the new `discord.SyncCacheAccessError`, whose message names the awaitable twin.

- **Twins** are named after the accessor they replace: `x` → `await get_x()`, `is_x()` → `await check_x()` (`is_usable()` → `check_usable()`, `is_assignable()` → `check_assignable()`, `is_nsfw()` → `check_nsfw()`, `can_send()` → `check_can_send()`), `permissions_for(obj)` → `get_permissions_for(obj)`, and `await is_chunked()` / `await is_permissions_synced()` for the boolean properties `chunked` / `permissions_synced`. A twin returns the same type as the accessor (`get_top_role()` is `Role | None` like `top_role`) and, for an attribute that falls back to a handle, the cached object or `None`.
- **Relationship attributes** return the cached object like pycord with the in-process cache, and a typed **partial handle** built from the id when it is not cached or the backend is remote (they never raise): `message.channel` / `PartialMessageable`, `message.guild`, `member.guild`, `role.guild`, `channel.guild`, `thread.guild` / `PartialGuild`, `thread.parent`, `channel.category`, `guild.afk_channel`, `voice_state.channel`, `scheduled_event.channel`, `stage_instance.channel` / `PartialGuildChannel`, `reaction.message` / `PartialMessage`, `thread_member.thread` and `parent` / `PartialMessageable`, `emoji.guild`, `sticker.guild`, `integration.guild`, `audit_log_entry.guild`, `scheduled_event.guild`, `stage_instance.guild`, `webhook.guild`, `webhook.channel`, `interaction.guild` (the partial guild of the payload when it has one), `VoiceChannelEffectSendEvent.guild`, the `guild`/`channel` of `RawVoiceStateUpdateEvent` and `RawVoiceServerUpdateEvent`, `ForwardedMessage.channel`/`guild`/`original_message`, `PartialMessage.guild`. Where pycord falls back to an object that only has an id, so do these: `PromptOption.channels`/`roles`, `WelcomeScreenChannel.channel`, `Onboarding.default_channels` and `ScheduledEventLocation.value` give the cached entity or an `Object`, `ForumChannel.default_reaction_emoji`, `PromptOption.emoji` and `WelcomeScreenChannel.emoji` the cached `GuildEmoji` or a `PartialEmoji`, and `Message.poll` the cached poll. They are resolved when read (never in a constructor), so they follow the cache.
- **Partial handles**: `PartialGuild` (`discord.guild`) with `get()`, `fetch()` and every REST action that only needs the id (`ban`, `kick`, `fetch_member`, `create_role`, `create_text_channel`, `fetch_channels`, ... the actions of `Guild` that do not read guild data, now provided by the shared `GuildActionsMixin`), `PartialGuildChannel` (`discord.channel`) with `get()` and `fetch()`, `PartialMessageable.get()` and `fetch()`, and `PartialMessage.get()` / `get_poll()` / `poll`.
- **`iter_*`**: `Guild.iter_members()` and `Client.iter_cached_messages()` stream the cached entities by batches of 100 instead of loading them all at once.
- **Ids that need no lookup**: `Member.guild_id`, `Role.guild_id`, `GuildChannel.guild_id`, `Thread.guild_id`, `Message.guild_id`, `Message.role_mention_ids`, `MessageCall.participant_ids`, `ForwardedMessage.role_mention_ids`, `Reaction.message_id`/`channel_id`/`guild_id`, `VoiceState.channel_id`/`guild_id`, `ScheduledEvent.guild_id`/`channel_id`, `StageInstance.guild_id`, `Interaction.user_id`, `AuditLogEntry.user_id`/`target_id`, `Template.source_guild_id`, `Guild.system_channel_id`/`rules_channel_id`/`public_updates_channel_id`/`afk_channel_id`, `emoji.role_ids`, and `guild_id`/`user_id`/`channel_id` on `VoiceChannelEffectSendEvent`.

**Other additions and behaviours of the cache wiring**

- `ConnectionState._create_message()` builds a message and resolves its cached author, mentions, roles, thread, emojis and poll results (the old constructor did it); `Message.edit()`, `Message.end_poll()` and the messages sent by webhooks go through it. `Invite.from_incomplete()` / `from_gateway()` keep resolving `invite.guild` / `invite.channel` from the in-process cache and give the payload objects (`PartialInviteGuild`/`PartialInviteChannel`) or partial handles with a remote backend.
- `Message.get_view()` returns the view tracked for the message (`ConnectionState.get_message_view()`), or builds one from the components (`DesignerView` for components v2, `View` otherwise) without registering it.
- `permissions_for()` and `get_permissions_for()` share one computation that follows the [Discord permissions documentation](https://docs.discord.com/developers/topics/permissions#permission-hierarchy): base permissions (owner, administrator), `@everyone` overwrite, role overwrites (denies then allows), member overwrite, then the implicit rules (no `send_messages` removes `send_tts_messages`, `mention_everyone`, `embed_links`, `attach_files`; no `read_messages` removes every channel permission) and the channel type rules. A member that is timed out only keeps `view_channel` and `read_message_history` in the channel, owners and administrators are exempt.
- `GuildChannel.changed_roles` returns copies of the roles with the overwrite applied to their permissions (the overwrite was applied to a temporary `Permissions` and lost). `GuildChannel.get_members()` exists on every guild channel.
- `Guild.large` counts the cached members when `member_count` is unknown (in-process cache), `repr(guild)` shows `chunked` with the in-process cache only.
- `Member.edit(suppress=...)`, `Member.request_to_speak()`, `Member.add_roles(atomic=False)` and `Member.remove_roles(atomic=False)` use the async getters, so they work with any cache backend. `Role.edit()` reads the guild features from the cache and no longer fails when the guild is not cached (the enhanced colours are then sent unchanged).
- Messages and raw events: `Attachment.is_spoiler()` also checks the `IS_SPOILER` flag (`AttachmentFlags.is_spoiler`), and `Attachment.with_changes(description=..., is_spoiler=...)` returns a copy to pass in `Message.edit(attachments=[...])`: "When editing, you must provide the `id` of each file to keep, and you can optionally update the `description` and `is_spoiler` fields of existing attachments" (Attachment Request Structure, message resource). `RawReactionActionEvent.message_author_id` (`message_author_id?` of the "Message Reaction Add Event Fields"). `PartialMessage` takes an optional keyword `guild_id` (`Reaction.message` and the message of a poll set it), so `reaction.users()` and `poll_answer.voters()` still yield `Member`s from the cache of a guild. `MessageSnapshot.message` is `None` when the snapshot has no message instead of being unset, and `MessagePinIterator` fills the pinned messages like `HistoryIterator` does. `Message.create_thread()` reads the default auto archive duration from the cached channel.
- Webhooks and templates: `Webhook.send(wait=True)`, `fetch_message()` and `edit_message()` build the message with the channel and guild of the payload and store its poll and author through the state (`WebhookMessage.edit()`/`delete()` find the thread or forum of the message through the async cache, so they work with any backend). `Template.source_guild` is the cached guild when there is one and else the guild serialised in the template; its helpers see an empty cache for the channels, roles and members. `ScheduledEvent.creator` is the member the caller resolved, or else the user of the payload, and `creator` is an optional keyword of the constructor.
- `ForumChannel.default_reaction_emoji`, `PromptOption.channels`/`roles`/`emoji`, `WelcomeScreenChannel.channel`/`emoji`, `ScheduledEventLocation.value` are properties that read the in-process cache when they are accessed; their constructors never read it.
- `ConnectionState.get_message_view()` and the properties `ConnectionState.guilds`, `emojis`, `stickers`, `polls`, `private_channels`, `sounds` (in-process cache).

### Gateway

- **Pluggable gateway transports** (`discord/gateway/`, `discord/gateway.py` is now a package and every previous import keeps working). The client no longer talks to a websocket: it consumes `GatewayEvent`s from a `ShardManager` that owns one `GatewayTransport` per shard. `DiscordGatewayTransport` (direct connection to Discord) is the default, so nothing changes without configuration; `Client(gateway=factory)` takes a `Callable[[shard_id, shard_count], GatewayTransport]` to read the events from somewhere else (a broker fed by a gateway proxy, for example). A transport implements `connect()`, `events()` (an async iterator of dispatch events), `send(op, d)`, `close()`, `latency`, `is_ratelimited()` and `is_closed()`; `change_presence`, `request_chunks`, `voice_state`, `request_soundboard_sounds` and `request_channel_info` (opcode 43, Request Channel Info; the `CHANNEL_INFO` event itself is task 5.1) are provided on top of `send()`.
- **`Client(gateway_compression=...)`**: `"zlib-stream"` (default, as before), `"zstd-stream"` (needs `pip install py-cord[zstd]`) or `None`. The IDENTIFY `compress` flag is no longer sent, Discord disables payload compression when transport compression is used and the library only handles transport compression.
- **Faster startup of big bots**: shards are launched in `max_concurrency` buckets (`shard_id % max_concurrency`, from Get Gateway Bot) that run in parallel, instead of one shard at a time with a fixed 5 seconds in between. An `IdentifyLimiter` still keeps 5 seconds between two IDENTIFYs of a bucket, also for shards that identify again later.
- **`on_gateway_rate_limited(payload)`** is dispatched when Discord answers a gateway request with a `RATE_LIMITED` event (`payload` is a `GatewayRateLimit` with `opcode`, `retry_after`, `meta`, `guild_id` and `nonce`). A Request Guild Members that was rate limited now fails `Guild.query_members()` / `Guild.chunk()` with `discord.GatewayRateLimited` (`opcode`, `retry_after`, `meta`) instead of waiting for the 30 seconds timeout.
- **`Client(large_threshold=...)`** (50 to 250, default 250 as before) and **`Client.session_start_limit`**, a `SessionStartLimit` object (`total`, `remaining`, `reset_after`, `max_concurrency` of the last Get Gateway Bot). New gateway APIs use keyword-only options and typed objects (`GatewayEvent`, `GatewayInfo`, `SessionStartLimit`, `GatewayRateLimit`, `Opcode`) so they can grow without breaking.

  ```python
  bot = discord.AutoShardedBot(gateway_compression="zstd-stream", large_threshold=100)
  print(bot.session_start_limit)

  def factory(shard_id, shard_count):
      return MyBrokerTransport(shard_id, shard_count)

  bot = discord.Bot(gateway=factory, shard_count=8)
  ```

- **Redis Streams gateway transport and `python -m discord gateway-proxy`** (opt-in, `pip install py-cord[redis]`). A gateway proxy keeps the connection to Discord and appends every raw dispatch event to `{prefix}:gateway:{shard_id}` (`MAXLEN ~ maxlen`, count based, 10000 by default, never time based); any number of workers read them with `Client(gateway=RedisStreamsTransport.factory(...))`. The proxy runs no cache and no parser, it only forwards events and executes the commands the workers append to `{prefix}:gateway:commands:{shard_id}` (presence, voice state, request guild members, soundboard sounds, channel info), so the rate limits of the gateway are applied once, by the proxy.
  - Workers are consumers of a Redis consumer group: `XREADGROUP`, then `XACK` once the client took the event. The group is created on the first start, a worker joining or restarting receives the `READY` of the live session from `{prefix}:gateway:session:{shard_id}` before anything else, and entries a crashed worker did not acknowledge are taken over (`XAUTOCLAIM`) by the others after `claim_idle_ms`. Workers of one group share the events of a shard, so they should share their cache (`cache_backend=RedisCache(...)`). `Client.latency` is the heartbeat latency measured by the proxy.
  - `RedisStreamsConfig` (keyword-only: `url` or `client`, `prefix`, `group`, `consumer`, `block_ms`, `batch_size`, `maxlen`, `claim_idle_ms`) configures `RedisStreamsTransport` and `RedisStreamsPublisher`, the building block the proxy uses and that can be reused to feed the streams from another source. The transport needs the `shard_count` of the proxy and raises a `ClientException` explaining it when it is missing. Other brokers only need a `GatewayTransport` implementation.
  - Both RESP2 and RESP3 clients (`protocol=3`) work: `XREADGROUP` replies are read as a list of streams (RESP2) or as a mapping of streams to entries (RESP3), whichever nesting redis-py returns.
  - `python -m discord gateway-proxy --token ... --redis-url ... --prefix ... --shard-ids 0-7,9 --shard-count 16 --intents ... --compression zlib-stream|zstd-stream|none --maxlen ... --log-level ...` stops cleanly on SIGINT and SIGTERM. The token can come from `DISCORD_TOKEN`; other subcommands keep working without `redis` installed.

  ```python
  from aiocache import RedisCache
  from discord.gateway.brokers import RedisStreamsTransport

  bot = discord.AutoShardedBot(
      shard_count=16,
      gateway=RedisStreamsTransport.factory(url="redis://localhost", prefix="mybot", group="workers"),
      cache_backend=RedisCache(endpoint="localhost"),
  )
  ```
  See `examples/redis_gateway/worker.py`.

### Commands

- **Slash command groups across cogs** (pycord-next). Several cogs can contribute subcommands and subgroups to the same `SlashCommandGroup`; the bot keeps one canonical group per name and set of guilds and sends a single payload. Each subcommand is bound to the cog that declares it (`self` is that cog), cogs load and unload in any order, and unloading a cog only removes the commands it declared. Previously a module level group used from two cogs registered nothing and turned `ctx` into an option, and a group shared as a class attribute made the last loaded cog win, registered duplicate groups and removed the wrong one on unload.
  - A cog can own the group by keeping it as a class attribute: its `cog_check` runs for every command of the group (before the group checks, the subgroup checks, the cog check of the cog that owns the leaf and the leaf checks) and its `cog_command_error` receives the errors of the other cogs' commands after theirs.
  - Two groups with the same name and guilds are merged. A duplicate subcommand name raises `ClientException` naming both cogs and leaves the bot untouched.
  - Loading or unloading a cog on a ready bot syncs the commands once, when `auto_sync_commands` is enabled (many cogs loaded in a row share one sync).
  - `BridgeCommandGroup` works the same way, including bridge subgroups ([pycord #3076](https://github.com/Pycord-Development/pycord/pull/3076)).
  - `BaseContext` (new, shared by `ApplicationContext` and `ext.commands.Context`) and the registry in `discord/commands/registry.py` are keyword-only and typed so they can grow without breaking.

  ```python
  admin = discord.SlashCommandGroup("admin", "Admin commands")

  class Moderation(discord.Cog):
      @admin.command()
      async def ban(self, ctx, member: discord.Member): ...

  class Settings(discord.Cog):
      config = admin.create_subgroup("config")

      @config.command()
      async def prefix(self, ctx, value: str): ...
  ```
  See `examples/app_commands/slash_multi_cog_groups.py`.

- **Smarter command auto-sync** ([pycord #2990](https://github.com/Pycord-Development/pycord/pull/2990) by Icebluewolf, reworked for pycord-next). `Bot.get_desynced_commands()` compares the commands field by field against the Discord application command object (`discord/commands/comparison.py`) instead of the old ad hoc checks, so a command is only edited when something really changed:
  - Fields that Discord fills with their documented defaults (`type` `1`, `nsfw` `false`, `default_member_permissions` `null`, empty `name_localizations` / `description_localizations`, `required` `false`, `autocomplete` `false`, empty `choices`, a missing `options`) are equal to the same field left out locally; changes to any field, option, choice, subcommand or subgroup, at any depth, are reported.
  - `default_member_permissions` is compared by value (Discord sends a string, the library sends an integer), `contexts`, `integration_types` and `channel_types` are compared as sets, and `contexts` / `integration_types` are ignored for guild commands, as Discord only stores them on global commands.
  - Commands are matched by name and type, so a slash command, a user command and a message command that share a name no longer shadow each other, and a remote command is only deleted when no local command has its name and type.
  - The rules are public and overridable: `DefaultComparison`, `DefaultSetComparison`, `COMMAND_DEFAULTS` and `Bot._get_command_defaults()`. A `"delete"` action carries the payload Discord returned as `command`.
- **Auto-sync keeps the entry point command.** A registered `PRIMARY_ENTRY_POINT` (type `4`) command that is not defined locally (the "Launch" command Discord creates when Activities are enabled, for example) is never deleted by `sync_commands()`: `Bot.get_desynced_commands()` reports it with the action `None`, the bulk overwrite sends it back unchanged (also with `force=True`, which reads the registered global commands for that), and the individual method leaves it alone. Delete or replace it explicitly ([Setting Up an Entry Point Command](https://docs.discord.com/developers/activities/development-guides/user-actions#setting-up-an-entry-point-command)) or define a local `EntryPointCommand` with its name.
- **Entry point commands** ([pycord #3276](https://github.com/Pycord-Development/pycord/pull/3276) by Icebluewolf). `EntryPointCommand`, `@discord.entry_point_command()` / `@bot.entry_point_command()` and `EntryPointHandler` (`app_handler`, `discord_launch_activity`) register the `PRIMARY_ENTRY_POINT` (type 4) command of an application with Activities. `InteractionResponse.launch_activity()` answers an interaction with callback type `LAUNCH_ACTIVITY` (12); `Interaction.activity_instance`, `InteractionCallback.activity_instance_id` and `InteractionCallbackActivityInstanceResource` expose the launched instance. Purely additive. Entry point commands are always global (`guild_ids` raises `InvalidArgument`, `debug_guilds` is not applied), work in cogs, and are compared by the auto-sync including `handler` (a command without `handler` accepts the one Discord has). See `examples/app_commands/entry_point.py`.

- **Cooldowns and max concurrency on every cache backend**. `BucketType.role` (top role of the author) and `BucketType.category` (category of the channel) need cache reads, so command invocation (application and prefix commands) now resolves the key through `await BucketType.get_key_async(msg)`, `await CooldownMapping.get_bucket_async()` / `update_rate_limit_async()` and `MaxConcurrency.acquire()` / `release()`: the role uses `Member.get_top_role()` (the guild id, i.e. `@everyone`, when the roles are not cached), the category uses the `category_id` of the channel and only looks a partial channel up with `get_channel()`. A callable bucket type given to `CooldownMapping` may be a coroutine function for the async path. The synchronous `get_bucket()`, `update_rate_limit()`, `BucketType.get_key()` and `MaxConcurrency.get_key()` are unchanged for the in-process cache (`is_on_cooldown()`, `reset_cooldown()` and `get_cooldown_retry_after()` still use them, so with a remote cache backend they raise `SyncCacheAccessError` for the role bucket).
- **`ext.commands` on every cache backend**. The converters resolve through the awaited lookups with the matching rules and order of pycord, so they work on the in-process cache and on a remote one: `MemberConverter` (id, mention, `name#discriminator`, name, nickname, global name, then the `Message.mentions` and the gateway/HTTP queries), `UserConverter`, `GuildConverter`, `RoleConverter`, `GuildChannelConverter` and the typed channel converters, `ThreadConverter`, `EmojiConverter`, `GuildStickerConverter`, `MessageConverter` and `PartialMessageConverter`; `clean_content` resolves the mentions it finds before substituting them. In a guild that is not cached, `MemberConverter` still queries the gateway or the HTTP API through the guild handle.
  - `Context.guild` and `Context.channel` follow the relationship rule (D12 of the cache wiring): the cached `Guild` / channel with the in-process cache, a `PartialGuild` / `PartialMessageable` handle when it is not cached or the backend is remote. `Context.author` is always the member from the message. `await Context.get_channel()` is the awaitable twin of `channel`; `get_guild()`, `me`, `get_me()` and `voice_client` come from `BaseContext`.
  - The role and permission checks await the cache: `has_role`, `has_permissions`, `bot_has_permissions`, `has_guild_permissions`... use `Member.get_roles()`, `Member.get_guild_permissions()` and `GuildChannel.get_permissions_for()`. A command invoked in a channel that is not cached fails the permission check instead of being granted. `is_nsfw` also works for threads on every backend. The documented `owner_or_permissions` example awaits `ctx.get_guild()`.
  - `ext.pages` needs no change: its `Paginator` only uses the context, interaction and message objects it is given. `ext.tasks` and `ext.bridge` are unchanged.

### Voice

- **DAVE E2EE voice receive** ([pycord #3159](https://github.com/Pycord-Development/pycord/pull/3159) by Paillat-dev). `VoiceClient.start_recording()` works on calls that use Discord's DAVE end-to-end encryption: the transport-decrypted RTP payload is DAVE-decrypted with the ssrc -> user mapping of the voice client (`VoiceClient._ssrc_to_id`, no dict rebuilt per packet), a payload that cannot be decrypted (`davey` raises `ValueError`, e.g. unencrypted while passthrough is disabled) or whose ssrc is not mapped yet is dropped instead of being decoded as silence, calls without DAVE (stage channels, protocol version 0) pass the payload through, and RTP padding is stripped (`RTPPacket.strip_padding`). PCM sinks decode inline (`PacketRouter.process_packet`), opus sinks (`Sink.is_opus()` returns `True`) go through the `JitterBuffer`. `Sink` gains `recording`, `is_opus()` and `walk_children()`, `Sink.init()` is called when recording starts, `Sink.write()` accepts `VoiceData` or `bytes`, and `WaveSink` writes a valid WAV (it used `VoiceClient.recording` and `VoiceClient.decoder`, which do not exist). `VoiceClient.start_recording()` and `is_speaking()` no longer emit the `RuntimeWarning` that reception is broken. The receive pipeline is typed (`AfterCallback` is a `Protocol`, `AudioReader` is generic over the callback arguments, RTCP report tuples are `NamedTuple`s).

  ```python
  async def finished(sink: discord.sinks.WaveSink, channel: discord.abc.Messageable):
      files = [discord.File(audio.file, f"{user_id}.wav") for user_id, audio in sink.audio_data.items()]
      await channel.send(files=files)

  vc.start_recording(discord.sinks.WaveSink(), finished, ctx.channel)
  ```

  `start_recording(sink, callback=None, *args, on_finish=None, sync_start=...)` keeps the 2.7 `callback(exception)` (and the 2.7 deprecation of `*args` without `on_finish`) and gains the keyword-only `on_finish`, called once and always as `on_finish(sink, *args)` after the sink was cleaned up (audio formatted), after `callback` when both are given; coroutine functions are scheduled on the client loop. `AfterCallback` is the `Protocol` of `on_finish`; `AudioReader(after=..., on_finish=..., args=...)` follows. `*args` go to `on_finish` and are only deprecated when it is not given. The recording examples use `on_finish`. Purely additive, `callback` behaves as in 2.7 (the upstream #3159 turned it into `callback(sink, *args)`, which would have broken it).

  Deliberately not taken from #3159: the lowercase renames of `HAS_DAVEY`, `HAS_NACL` and `DAVE_PROTOCOL_VERSION` in `discord.voice.utils.dependencies` (cosmetic, they would break anyone importing the constants), the unconditional `import davey` in the voice modules (`import discord.voice` already raises `MissingVoiceDependenciesError` first, the conditional imports are kept), and `set_passthrough_mode(True, 10)` -> `120`: the second argument of `davey.DaveSession.set_passthrough_mode` is "the transition expiry to use when disabling passthrough mode, defaults to 10 seconds", so it has no effect when enabling it, and the DAVE whitepaper keeps previous ratchets "for a period of up to ten seconds".
- **`protocol_whitelist` for `FFmpegPCMAudio`, `FFmpegOpusAudio`, `FFmpegOpusAudio.from_probe()` and `probe()`** ([pycord #3225](https://github.com/Pycord-Development/pycord/pull/3225) by Paillat-dev, opt-in here). A keyword-only `protocol_whitelist: Sequence[str] | None = None` passes `-protocol_whitelist` to ffmpeg (and ffprobe) before `-i`. The default keeps the behaviour of every release (no restriction), so `concat:`, `subfile:` and `data:` inputs keep working; upstream turned the whitelist on for everybody. When the source can be influenced by users, pass `protocol_whitelist=discord.player.RECOMMENDED_PROTOCOL_WHITELIST` (`file,http,https,tcp,tls,crypto,pipe,fd,cache`). It is ignored with a `UserWarning` when `before_options` already contains `-protocol_whitelist`. The docstrings of both classes now warn that `source` reaches ffmpeg's `-i` untouched (local file read, SSRF, `concat:`).

- **Voice receive resolves members without touching the cache from threads.** The voice client looks up the member of a speaking, connecting or disconnecting user on the event loop (`member_speaking_state_update`, `member_connect`, `member_disconnect`) and keeps it in a plain per-client map; the router and speaking-timer threads (and `PacketDecoder` for `VoiceData.source`) only read that map, and ask the loop to resolve a missing user through `call_soon_threadsafe` (once per user, not once per packet). It works with any cache backend. `VoiceClient.guild` is typed `Guild | PartialGuild`, the connection state reads the guild voice state and channels through awaited lookups, and our own SSRC uses `VoiceClient.user` instead of `guild.me`.

- `discord/http.py` is split into the `discord/http/` package (`route`, `ratelimit`, `multipart`, `base`, one `routes/<resource>.py` mixin per Discord resource, composed in `client`), following [#3220](https://github.com/Pycord-Development/pycord/issues/3220) and [#3222](https://github.com/Pycord-Development/pycord/issues/3222). `from discord.http import HTTPClient, Route, API_VERSION` and every `HTTPClient` method keep working unchanged; `HTTPClient.request` is split into `_prepare`, `_send` and `_handle_response`, and the rate limit logic lives in `RateLimiter`.
- The name-mangled `HTTPClient.__session` is now `HTTPClient._session`.
- `tests/http/` checks every endpoint automatically (verb, URL, audit log reason, resource module) and covers rate limits (`aioresponses`), multipart uploads and the session lifecycle.
- `discord/state.py` is split into the `discord/state/` package: `state` (`ConnectionState`, `ChunkRequest`), `sharded` (`AutoShardedConnectionState`) and one `parsers/<resource>.py` module per Discord resource (77 gateway events). Parsers are module level functions `parse_x(state, data)` typed with the gateway event TypedDict where one exists, collected in `discord.state.parsers.PARSERS` (`{EVENT_NAME: function}`); `ConnectionState.parsers` keeps its shape (event name to callable taking `data`), and a state subclass defining a `parse_x` method still overrides the registry parser (`AutoShardedConnectionState` does for `READY` and `RESUMED`). `from discord.state import ConnectionState, AutoShardedConnectionState, ChunkRequest` is unchanged.
- The parsers share small helpers instead of repeating the same blocks (unknown guild logging, member of a raw reaction/typing event, poll voter lookup, scheduled event creation and subscriber count). Tasks spawned by parsers (modal dispatch, member chunking after `GUILD_CREATE`, voice protocol callbacks) are kept referenced until they finish (`ConnectionState._create_task`) so they cannot be garbage collected mid-run.
- `tests/state/` checks that every gateway event handled before the split still has a parser, that `AutoShardedConnectionState` overrides win, and replays a `READY`, `GUILD_CREATE`, `CHANNEL_CREATE`, `MESSAGE_CREATE`, `GUILD_MEMBER_*` and `THREAD_*` sequence through `state.parsers`.
- The `discord.ui` items no longer re-declare the parameters, validation and property boilerplate of their `discord.components` counterpart. `discord/ui/_fields.py` provides `Field`, a property forwarding to the underlying component whose checks (types, `ComponentLimits` ranges and lengths, option lists) run both when the item is constructed and when the attribute is assigned, so each limit is declared once. `Item` builds the underlying component from the constructor values (`_build_underlying`), snapshots it generically (`_generate_underlying`, containers only re-attach their children) and rebuilds an item from a component (`from_component`) from the declared fields. `Button`, `Select`, `InputText`, `TextDisplay`, `Separator`, `Thumbnail`, `File`, `MediaGallery`, `Container`, `Label`, `FileUpload`, `RadioGroup`, `CheckboxGroup` and `Checkbox` keep the same constructors, keyword arguments, properties, setters, defaults and docstrings. `discord/ui` goes from 8713 to 8083 lines (`components.py` is unchanged), and pyright reports 338 fewer errors on `discord/ui` and `discord/components.py`.
- Behavior notes of that refactor: constructors now run the same checks as the setters (for example `ui.MediaGallery(*items)` rejects more than 10 items and non `MediaGalleryItem` values, and wrong types raise `TypeError` instead of being stored), error messages are unified (`"<attribute> must be <n> characters or fewer"`, `"<attribute> must be between <a> and <b>"`), `Button.label` is stored as `str` also from the constructor, and `RadioGroup`, `CheckboxGroup` and `Checkbox` rebuild their data in `from_component` instead of returning an empty item. The properties are `Field` objects (subclasses of `property`), so Sphinx still lists them but no longer shows their return annotation.
- `tests/ui/test_component_parity.py` checks every `discord.ui` item against its `discord.components` class: each constructor parameter (derived from the signature) is exercised, `to_component_dict()` equals `to_dict()` of the component built from the same payload, `from_component` round-trips, every public attribute of the component class is reachable on the item with the same value, and assigning each field reaches the component.

- `Webhook` and `SyncWebhook` run on one core, `discord/webhook/_core.py`. A pure layer builds the requests (routes, headers, JSON or multipart bodies, query parameters, `send`/`edit_message`/`edit`/`fetch`/`delete` validation through `WebhookRequests`, shared by both classes) and applies the rate limit and retry policy (`Execution`: `429` bucket, global and Cloudflare, `5xx` backoff, connection reset, exhausted bucket pause, error mapping). `AsyncWebhookAdapter` (aiohttp) and `WebhookAdapter` (requests) only send what the core prepared and sleep for the delays it returns, so the two clients can no longer drift apart. The public classes, signatures and return types of `Webhook`, `SyncWebhook`, `WebhookMessage`, `SyncWebhookMessage`, `PartialWebhookChannel` and `PartialWebhookGuild` are unchanged, and `SyncWebhook` stays synchronous and never reads the async cache.
